# Issue: UIの改善、複数行入力のサポート、およびキャンセル時の入力復帰

## 背景と問題点
- 現状の入力UI（幅400px）が小さく、長めの検索クエリの視認性が低い。
- 入力欄に説明文が表示されているが、操作に慣れたユーザーにとってはノイズであり、入力を阻害している。
- 複雑なプロンプトや複数行の入力を扱う手段がなく、単一行の検索に限定されている。
- アクション選択画面でキャンセル（Esc）を押すとアプリケーションが終了してしまい、入力ミスがあった場合に最初から入力をやり直す必要がある。

## 解決策
- **入力UIの最適化**: `bin/inquery` の初期入力ウィンドウを 800px に拡大し、テキストを空にすることで入力欄を主役にする。
- **複数行入力モードの導入**: 初期の入力欄で `..` と入力した場合、`zenity --text-info` を起動して複数行の編集を可能にする。
- **改行時のアクション絞り込み**: クエリに改行が含まれている場合、`copy_to_clipboard: true` が設定されているアクションのみを表示候補とする（URL置換によるエラーを防止するため）。改行が含まれない場合は、通常通りのフィルタリングを行う。
- **改行時のクリップボード強制コピー**: クエリに改行が含まれている場合、アクションの設定に関わらず、実行時にクエリをクリップボードに強制コピーする。

## 修正対象
- `bin/inquery`: `while` ループによる入力・選択フローの制御、クエリ保持、複数行遷移ロジックの実装。
- `lib/ui.sh`: キャンセル時に非0の終了コードを返すようにし、ウィンドウ幅を 800px に調整。
- `lib/filter.py`: 改行検出時のアクション絞り込みロジックの追加。
- `lib/executor.py`: 改行検出時のクリップボード強制コピーロジックの追加。

## 実装内容詳細

### 1. 入力ループの論理的構造 (`bin/inquery`)
プロセスの入れ子構造によってモード遷移を論理的に管理する。
- **第一階層 (Entryモード)**: 1行入力を受け付ける `while` ループ。
    - `zenity --entry` で入力を取得。
    - キャンセル時はアプリ終了。
    - `..` 入力時は **第二階層** へ。
    - それ以外のアクション選択キャンセル時は、第一階層の入力（1行入力）を再試行。
- **第二階層 (Multi-lineモード)**: 複数行入力を受け付ける内部 `while` ループ。
    - `zenity --text-info` で入力を取得。
    - キャンセル時は第二階層を抜け（`break`）、第一階層の入力（1行入力）へ戻る。
    - 入力確定後のアクション選択キャンセル時は、第二階層の入力（複数行入力）を再試行。

### 2. 初期入力UIの変更 (`bin/inquery`)
- `zenity --entry` の引数を調整:
    - `--width=800`
    - `--title="inquery ('..' for multi-line)"` (1行入力モード時のみ案内をタイトルに表示)
    - `--text=""` (入力欄上部をクリーンに保つ)
- 入力結果が `..` の場合、以下のコマンドで上書きする:
    - `zenity --text-info --editable --title="inquery (ctrl+enter to submit)" --width=800 --height=600` (複数行モード時の確定方法をタイトルで案内)

### 3. `lib/ui.sh` のインターフェース調整
- `zenity --list` のウィンドウ幅も 800px 程度に広げ、入力画面との視覚的な連続性を確保する。

## Appendix: 技術的選定理由 (Why/Why not)
- **なぜ `while` ループか？**
  - プロセスの蓄積（再帰の回避）を防ぎつつ、クエリ変数をループ内で容易に保持・共有できるため。
- **なぜ入力画面に戻るのか？**
  - 入力を間違えた際、最初から入力をやり直す手間を省き、復元された内容を修正可能にするため。
- **なぜ Zenity を使い続けるのか？**
  - 高速性とシンプルさを維持するため。GTK や PyGObject を導入すれば高度な UI は可能だが、依存関係の複雑化と起動速度の低下を招く。現状の「名詞先行・動詞後選択」のワークフローには、軽量な Zenity が最適であると判断。
- **なぜ OK/キャンセルボタンを消さないのか？**
  - inquery のユーザー層にとって Enter（確定）と Esc（キャンセル）による操作は自明であるが、Zenity の標準仕様では、ボタンの完全な非表示化はできない。
- **なぜ改行時にアクションを絞り込むのか？**
  - 改行を含むクエリを URL 置換に利用すると、不正な URL が生成されブラウザ等でエラーになるリスクがあるため。`copy_to_clipboard: true` のアクションに限定することで、安全に情報を外部へ持ち出せるようにする。
- **なぜ改行時にクリップボードへ強制コピーするのか？**
  - 改行を含む複雑なプロンプトや文章は、ブラウザ等の入力欄に自動で流し込むのが難しい（または失敗する）場合がある。クリップボードに保持しておくことで、ユーザーが必要な場所へ確実に貼り付けられるようにするため。
- **なぜ `..` か？**
  - ホームポジションから近く、プレフィックス入力を避けつつ「特別なモード」を明示するための最小限のシークエンスとして採用。
