# Issue: フィルタリングロジックの改修および Repository パターンの導入

## 背景と問題点
- 現在の `lib/filter.py` 内の関数が、入力クエリでアクションの「ラベル名」を絞り込んでおり、「名詞先行・動詞後選択」の設計原則が破壊されている。
- 1つの関数に設定の読み込み、フィルタリング、結果の出力の責務が集中し、保守性が低い。
- `config/actions.json` に冗長な `type` プロパティが存在し、設定ミスの原因となっている。

## 解決策
- ラベル名マッチングを廃止し、絞り込みを `show_if_contains` および改行条件のみに限定する。
- Repository パターンを導入し、データモデルとドメインロジックを `lib/actions.py` に分離する。
- `actions.json` から `type` を廃止し、`url` と `script` の存在で実行タイプを自動判別する（`url` 優先）。
- `lib/executor.py` から重複する設定読み込みロジックを排除し、`lib/actions.py` に依存させる。

## 実装内容詳細 (Atomic Steps)

### Step 1: `config/actions.json` のスキーマ簡素化
- `type` プロパティを全アクション定義から削除する。

### Step 2: `lib/actions.py` の新規作成 (Repository パターンの導入)
- `Action` クラス: アクションのデータモデルを定義。`__init__` にて `type` を `url` または `script` プロパティから自動判別する。
- `ActionRepository` クラス: `actions.json` からデータを読み込み、`Action` オブジェクトのリストを提供する `list_all()` メソッドを実装する。
- `ActionFilter` クラス: クエリ文字列に基づき、`show_if_contains` などの条件を満たすアクションのみを抽出するフィルタリングロジックを実装する。
- `ActionOrchestrator` クラス: `Repository` と `Filter` を統合し、入出力のパイプラインを指揮するインターフェースを提供する。

### Step 3: `lib/filter.py` の改修
- 既存の責務過多な関数を廃止する。
- `lib/actions.py` の `ActionOrchestrator` を呼び出してフィルタリング結果を取得するよう再実装する。
- ラベル名によるマッチング処理を**完全削除**する。

### Step 4: `lib/executor.py` の改修
- `actions.json` を直接パースする重複コードを削除する。
- `lib/actions.py` の `ActionRepository` を使用して、選択されたアクションを取得するようリファクタリングする。

## 規約準拠 (Rule Compliance)

- **`comment-preservation.md`**: `lib/filter.py` や `lib/executor.py` をリファクタリングする際、削除・改修されるロジックに関連する既存のコメントや JSDoc（Python の場合は Docstring）は削除せず、Repository パターンに基づく新しいコンテキストに合わせて正確に更新する。

- [x] クエリに改行が含まれる場合、`copy_to_clipboard: true` のアクションのみが表示される。
- [x] 設定読み込み、フィルタリング、出力の責務が `lib/actions.py` に分離されている。
- [x] JSONスキーマから `type` が廃止され、`url` 優先で動作タイプが自動判別される。
- [x] 既存のテストおよび新規追加するテストが全てパスする。
- [x] **`comment-preservation.md` 準拠**: リファクタリング対象ファイルのコメント（Docstring）が新しい仕様に合わせて更新されている。

## Appendix: 技術的選定理由 (Why/Why Not)

- Repository パターンの導入: フィルタリングと設定ファイル読み込みが単一関数に集中していたため、保守性とテスト容易性を高める目的でデータアクセス層 (`ActionRepository`) とロジック層 (`ActionFilter`) に分割した。
